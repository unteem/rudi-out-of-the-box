## Certificate Strategy

### Internal Microservices Communication

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│   ACL    │────>│ Registry │<────│ Gateway  │
└──────────┘     └──────────┘     └──────────┘
     │                                   │
     └───────────> Same Certificate <────┘
        CN=rudi.yourdomain.com
        SAN=registry,acl,gateway,localhost,...
```

**Approach**: ✅ **One certificate shared by all internal microservices**

### External-Facing Services

```
Internet ──> Traefik ──> Microservices (internal)
             │
             └─> Uses: Public SSL Cert (Let's Encrypt)
                 
Microservices ──> Microservices
    │
    └─> Uses: Internal SSL Cert (self-signed or internal CA)
```

**Approach**: 
- ✅ **Public certificate** for Traefik (wildcard or multi-domain)
- ✅ **Internal certificate** for microservice-to-microservice (can be self-signed)

## Why Same Certificate for All Services?

### ✅ Advantages

1. **Simplified Management**
   - One certificate to generate
   - One certificate to renew
   - One certificate to rotate
   - Easier automation

2. **Easier Trust Configuration**
   - All services trust the same CA certificate
   - Simplified truststore configuration
   - No need for complex certificate chains

3. **Reduced Complexity**
   - Fewer moving parts
   - Easier debugging (all services behave the same)
   - Simpler deployment scripts

4. **Cost Effective**
   - One wildcard certificate covers all services
   - Or one self-signed certificate for internal use

5. **Standard Practice**
   - Used by Kubernetes (single CA for all pods)
   - Used by service meshes (Istio, Linkerd)
   - Recommended by microservices best practices

### ❌ When to Use Different Certificates

Only use different certificates when:

1. **Different external domains**
   ```
   api.company.com  → Certificate A
   portal.company.com → Certificate B
   ```

2. **Different security zones**
   ```
   dmz-services     → Public CA certificate
   internal-services → Internal CA certificate
   ```

3. **Compliance requirements**
   - PCI-DSS might require separate certificates per security level
   - Industry-specific regulations

4. **Different certificate lifecycles**
   - Short-lived certificates for high-security services
   - Long-lived certificates for stable services

## Subject Alternative Names (SAN)

### What is SAN?

Subject Alternative Name (SAN) is an X.509 certificate extension that allows a certificate to specify **multiple hostnames** it's valid for.

### Example Certificate

```
Certificate:
  Subject: CN=rudi.yourdomain.com
  Subject Alternative Name:
    DNS:registry
    DNS:acl
    DNS:apigateway
    DNS:gateway
    DNS:kalim
    DNS:konsent
    DNS:konsult
    DNS:kos
    DNS:projekt
    DNS:selfdata
    DNS:strukture
    DNS:localhost
    DNS:rudi.yourdomain.com
    DNS:dataverse.yourdomain.com
    DNS:magnolia.yourdomain.com
    DNS:*.yourdomain.com
```

### Why SAN Matters

When service `acl` connects to `registry`:
1. Opens SSL connection to hostname: `registry`
2. Receives certificate with CN=`rudi.yourdomain.com`
3. Java checks: Does certificate cover hostname `registry`?
4. ✅ YES: SAN includes `DNS:registry`
5. Connection succeeds

Without SAN:
- ❌ Certificate only valid for `rudi.yourdomain.com`
- ❌ Connection to `registry` fails with: `SSLPeerUnverifiedException`

## Development vs Production

### Development Environment

**Use**: Self-signed certificate with comprehensive SANs

```bash
# Generated by scripts/generate-ssl-keystores.sh
openssl req -x509 -nodes -days 365 -newkey rsa:4096 \
  -keyout privkey.pem \
  -out fullchain.pem \
  -subj "/CN=rudi.localhost" \
  -addext "subjectAltName=DNS:registry,DNS:acl,DNS:apigateway,DNS:gateway,\
DNS:kalim,DNS:konsent,DNS:konsult,DNS:kos,DNS:projekt,DNS:selfdata,\
DNS:strukture,DNS:localhost,DNS:*.localhost"
```

**OR** use `trust-all-certs=true` in properties files:
```properties
trust.trust-all-certs=true  # Disables hostname verification
```

⚠️ **WARNING**: `trust-all-certs=true` is **ONLY** for development!

### Production Environment

**Option 1: Wildcard Certificate (Recommended)**

Obtain a wildcard certificate for `*.yourdomain.com`:

```
Covers:
  ✅ rudi.yourdomain.com
  ✅ dataverse.yourdomain.com
  ✅ magnolia.yourdomain.com
```

**BUT** still needs explicit SANs for Docker service names:
- Add `DNS:registry,DNS:acl,DNS:gateway,...` as SANs

**Option 2: Multi-Domain Certificate**

Certificate with explicit SANs for all needed hostnames:

```
SAN:
  DNS:rudi.yourdomain.com
  DNS:dataverse.yourdomain.com
  DNS:magnolia.yourdomain.com
  DNS:registry
  DNS:acl
  DNS:gateway
  ... (all microservice names)
```

**Option 3: Two-Tier Certificate Strategy** (Most Secure)

```
Public-facing:
  Traefik → Let's Encrypt wildcard cert (*.yourdomain.com)
  
Internal:
  Microservices → Internal CA certificate (self-signed or corporate CA)
  With SANs for all service names
```

Benefits:
- Public certificate managed by Let's Encrypt (auto-renewal)
- Internal certificate doesn't need to be publicly trusted
- Can use longer validity periods for internal cert
- Security isolation

## Certificate Generation

### Using RUDI Scripts

#### 1. Generate Self-Signed Certificate (Development)

```bash
cd /path/to/rudi-out-of-the-box

# Script will prompt to generate self-signed if no certificate found
./scripts/generate-ssl-keystores.sh

# Or explicitly generate first
mkdir -p certs
openssl req -x509 -nodes -days 365 -newkey rsa:4096 \
  -keyout certs/privkey.pem \
  -out certs/fullchain.pem \
  -subj "/CN=rudi.localhost" \
  -addext "subjectAltName=DNS:registry,DNS:acl,DNS:apigateway,DNS:gateway,\
DNS:kalim,DNS:konsent,DNS:konsult,DNS:kos,DNS:projekt,DNS:selfdata,\
DNS:strukture,DNS:localhost,DNS:*.localhost"

# Then generate keystores
./scripts/generate-ssl-keystores.sh
```

#### 2. Use Let's Encrypt (Production)

```bash
# Obtain Let's Encrypt certificate
sudo certbot certonly --standalone -d rudi.yourdomain.com \
  -d dataverse.yourdomain.com \
  -d magnolia.yourdomain.com

# Copy certificates
mkdir -p certs
sudo cp /etc/letsencrypt/live/rudi.yourdomain.com/fullchain.pem certs/
sudo cp /etc/letsencrypt/live/rudi.yourdomain.com/privkey.pem certs/
sudo chown $USER:$USER certs/*.pem

# Generate keystores
./scripts/generate-ssl-keystores.sh
```

⚠️ **Problem**: Let's Encrypt certificates don't include Docker service names as SANs!

**Solution**: Create a two-tier setup or use `trust-all-certs=true` for internal communication.

#### 3. Corporate CA Certificate (Production)

```bash
# Obtain certificate from your corporate CA
# Ensure it includes SANs for all service names

# Place certificates
cp /path/to/fullchain.pem certs/
cp /path/to/privkey.pem certs/

# Generate keystores
./scripts/generate-ssl-keystores.sh
```

## Current Script Behavior

The `scripts/generate-ssl-keystores.sh` script:

1. ✅ Takes **ONE** PEM certificate + key
2. ✅ Converts to PKCS12 keystore format
3. ✅ **Copies the SAME keystore** to all service directories
4. ✅ Generates special keystores (consent, selfdata) for specific purposes

```bash
# This is CORRECT and follows best practices!
for service in "${SERVICES[@]}"; do
  openssl pkcs12 -export \
    -in "$CERT_FILE" \           # Same certificate
    -inkey "$KEY_FILE" \          # Same key
    -out "config/$service/rudi-https-certificate.jks" \
    -name "rudi-https" \
    -password "pass:$PASSWORD"
done
```

**Result**: All services have **identical** `rudi-https-certificate.jks` files.

**Is this correct?** ✅ **YES!** This is the standard approach.

## Troubleshooting

### Error: Certificate doesn't match hostname

```
SSLPeerUnverifiedException: Certificate for <registry> doesn't match 
common name of the certificate subject: rudi.yourdomain.com
```

**Cause**: Certificate doesn't include `registry` in SAN

**Solutions**:

1. **Development**: Enable trust-all-certs
   ```properties
   trust.trust-all-certs=true
   ```

2. **Production**: Regenerate certificate with proper SANs
   ```bash
   ./scripts/generate-ssl-keystores.sh
   # Make sure it includes all service names in SAN
   ```

3. **Verify certificate SANs**:
   ```bash
   keytool -list -v -keystore config/registry/rudi-https-certificate.jks \
     -storepass "$KEYSTORE_PASSWORD" | grep -A 5 "SubjectAlternativeName"
   ```

### Error: Unable to find valid certification path

```
ValidatorException: PKIX path building failed
```

**Cause**: Java doesn't trust the certificate CA

**Solutions**:

1. **Self-signed cert**: Enable trust-all-certs (development)
2. **Production**: Import CA certificate into Java truststore
   ```bash
   keytool -import -trustcacerts -alias rudica \
     -file ca-cert.pem \
     -keystore $JAVA_HOME/lib/security/cacerts \
     -storepass changeit
   ```

### Checking Certificate Details

```bash
# View certificate in PEM format
openssl x509 -in certs/fullchain.pem -text -noout

# View certificate in keystore
keytool -list -v -keystore config/registry/rudi-https-certificate.jks \
  -storepass "$KEYSTORE_PASSWORD"

# Test SSL connection
openssl s_client -connect registry:8761 -servername registry

# From inside container
docker compose exec acl \
  openssl s_client -connect registry:8761 -servername registry
```
